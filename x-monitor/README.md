# X Monitor — мониторинг аккаунтов X (Twitter) с уведомлениями в Telegram

Сервис отслеживает выбранные аккаунты X и присылает в Telegram уведомления, когда они:

| Действие | Тип события |
|---|---|
| публикуют новый пост | 📝 `post` |
| отвечают на публикацию / оставляют комментарий | 💬 `reply` |
| делают репост | 🔁 `repost` |
| публикуют цитату (Quote Post) | 🗨 `quote` |

Всё управление идёт через Telegram-бота с inline-кнопками: аккаунты, уведомления, настройки, история, статистика.

## 1. Проверка технической реализуемости (Этап 2)

Проверялось по официальной документации X и по OpenAPI-спецификации `https://api.x.com/2/openapi.json` (v2.174, ноябрь 2026).

### Источник данных: официальный X API v2

`GET /2/users/{id}/tweets` — лента пользователя. Возвращает **все четыре нужных типа активности**:

| Тип | Как определяется |
|---|---|
| Пост | нет `referenced_tweets` |
| Ответ / комментарий | `referenced_tweets[].type = "replied_to"` (+ `in_reply_to_user_id`) |
| Репост | `referenced_tweets[].type = "retweeted"` |
| Цитата | `referenced_tweets[].type = "quoted"` |

Параметр `since_id` возвращает только посты новее последнего обработанного, поэтому опрос дёшев. Через `expansions` подгружаются оригинал репоста, цитируемый пост, автор поста, на который отвечают, и медиа.

### Реальные ограничения (важно знать)

* **Нужен платный доступ.** С февраля 2026 у X API нет бесплатного уровня и подписок Basic/Pro: оплата pay-per-use через предоплаченные кредиты в console.x.com.
  * чтение поста ≈ **$0.005**, чтение профиля ≈ **$0.010** (при добавлении аккаунта);
  * один и тот же ресурс, по документации, обычно оплачивается один раз в сутки (UTC);
  * лимит 3 млн прочитанных постов в месяц (дальше нужен Enterprise).
  * Тарифицируются возвращённые ресурсы. Списывается ли что-то за пустой ответ, в документации не сказано — проверьте расход в console.x.com в первые дни.
* **Это опрос, а не push.** Задержка уведомления примерно равна частоте проверки (по умолчанию 60 с, минимум 5 с). Лимит эндпоинта — 10 000 запросов за 15 минут на приложение: при интервале 60 с хватает примерно на 600 аккаунтов, при 5 с — примерно на 55. Real-time стрим (`/2/tweets/search/stream`, правило `from:username`) X документирует с ограничением в одно соединение. Доступен ли он на pay-per-use, документация не говорит, поэтому в v1 он не используется. Архитектура позволяет добавить его как ещё один источник событий (см. раздел 9).
* **Закрытые (protected) аккаунты недоступны** с app-only токеном: бот откажет при добавлении.
* Если пост удалили до ближайшей проверки, он не будет обнаружен.
* Лайки не отслеживаются (их не было в задаче, и это отдельный эндпоинт).
* **Переименование полей.** В свежей OpenAPI-спецификации параметры переименованы (`tweet.fields` → `post.fields`, `referenced_tweets` → `referenced_posts`), а в data dictionary остались старые имена. Без ключа нельзя проверить, какие имена принимает боевой API, поэтому клиент работает в режиме `X_API_PARAM_DIALECT=auto`. Начинает со старых имён, а при ответе 400 о неизвестном параметре один раз переключается на новые. Ответ разбирается в обоих вариантах.

Альтернативы вроде Nitter, скрейпинга или неофициальных «прокси-API» не используются: они нарушают условия X или нестабильны.

## 2. Архитектура

```
Telegram ⇄ aiogram (handlers, middlewares) ──┐
                                            ├── PostgreSQL (SQLAlchemy 2, Alembic)
APScheduler ─ Monitor ─ XClient ─ X API v2 ──┤
           └ NotificationDispatcher ─ Telegram (outbox)
Redis: состояние диалогов (FSM), кэш профилей X        FastAPI: /health
```

* **Monitor** раз в `MONITOR_TICK_SECONDS` выбирает аккаунты, которым пора на проверку (`next_check_at`), и атомарно «захватывает» каждый. Затем запрашивает ленту с `since_id = last_seen_post_id` и **в одной транзакции** сохраняет события, создаёт уведомления и сдвигает `last_seen_post_id`.
* **NotificationDispatcher** (outbox-паттерн) читает очередь `notifications` (`FOR UPDATE SKIP LOCKED`), учитывает тихие часы и группировку и отправляет сообщения в Telegram.
* Аккаунт X хранится один раз, даже если его отслеживают несколько пользователей: один запрос к API обслуживает всех подписчиков.

### Защита от дубликатов

1. `events.post_id` — **UNIQUE**, вставка через `INSERT … ON CONFLICT DO NOTHING`. Уведомление создаётся, только если строка реально вставлена.
2. `notifications (event_id, user_id)` — **UNIQUE**.
3. `last_seen_post_id` хранится в БД и сдвигается в той же транзакции, поэтому после перезапуска опрос продолжается с того же места.
4. Доставка «не более одного раза»: статус `sending` фиксируется **до** отправки. Если процесс упал посреди отправки, такие строки при старте считаются доставленными. Лучше потерять одно сообщение в момент аварии, чем прислать дубль.

### Без «потока старых постов»

При добавлении аккаунта `last_seen_post_id` выставляется в Snowflake-ID текущего момента, который вычисляется локально и не стоит денег. Поэтому приходят уведомления только о действиях после добавления. То же самое при снятии с паузы, если аккаунт в это время никто не отслеживал.

### Надёжность

* Ретраи с экспоненциальной задержкой на сетевые ошибки и 5xx.
* Учёт `x-rate-limit-remaining/reset`: клиент перестаёт слать запросы до сброса лимита, а на 429 переносит проверку.
* Ошибки отдельного аккаунта (удалён, заблокирован, закрыт) увеличивают интервал проверки: до 30 минут для временных ошибок и до 6 часов для недоступных аккаунтов. После N неудач подряд приходит оповещение, после восстановления — сообщение «восстановлен».
* Глобальные ошибки (401 — неверный токен, 402 — нет кредитов, 403 — нет доступа) присылаются не чаще раза в час.
* Ограничения Telegram: при flood control доставка приостанавливается на `retry_after`. Если пользователь заблокировал бота, уведомление помечается `failed` без бесконечных повторов.

## 3. Что нужно получить

### Telegram-бот
1. Откройте [@BotFather](https://t.me/BotFather) → `/newbot` → задайте имя и username.
2. Скопируйте токен (`123456789:AA…`) в `TELEGRAM_BOT_TOKEN`.

### Ваш Telegram ID
Напишите [@userinfobot](https://t.me/userinfobot). Другой способ: запустите бота и отправьте ему `/start`, он ответит «Доступ запрещён» и покажет ваш ID. Впишите ID в `TELEGRAM_ALLOWED_USER_IDS` (несколько ID — через запятую). Пользователям не из списка бот не отвечает ничем, кроме отказа.

### X API Bearer Token
1. Зайдите на [console.x.com](https://console.x.com) и примите Developer Agreement.
2. Создайте проект и приложение (App).
3. Пополните кредиты (Billing): без баланса API отвечает `402 Payment Required`.
4. В приложении: **Keys and tokens → Bearer Token → Generate**, затем скопируйте его в `X_BEARER_TOKEN`.

Примерная стоимость: 10 аккаунтов × 20 действий в день = 200 постов в день ≈ **$1 в день (~$30 в месяц)**. Репосты, цитаты и ответы подгружают оригинальный пост, что может удвоить число прочитанных постов. Если важна экономия, `X_FETCH_REFERENCES=false` отключает подгрузку оригиналов. Добавление аккаунта ≈ $0.01.

## 4. Запуск через Docker Compose (рекомендуется)

```bash
cd x-monitor
cp .env.example .env
nano .env              # TELEGRAM_BOT_TOKEN, TELEGRAM_ALLOWED_USER_IDS, X_BEARER_TOKEN, POSTGRES_PASSWORD
docker compose up -d --build
docker compose logs -f app
```

* Миграции применяются автоматически при старте контейнера `app`.
* Сервисы: `db` (PostgreSQL 16), `redis`, `app`, `backup`. Перезапуск: `restart: unless-stopped`.
* Проверка: `curl http://127.0.0.1:8080/health`.
* Затем откройте бота в Telegram, отправьте `/start` и нажмите «➕ Добавить аккаунт».

Обновление: `git pull && docker compose up -d --build`.

## 5. Запуск без Docker

Нужны Python 3.12+, PostgreSQL 14+ и, по желанию, Redis.

```bash
cd x-monitor
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # заполните и раскомментируйте DATABASE_URL (и REDIS_URL)
alembic upgrade head
python main.py
```

Без `REDIS_URL` состояние диалогов хранится в памяти. Все настройки, аккаунты и история хранятся в PostgreSQL и переживают перезапуск в любом случае.

## 7. Безопасность и бэкапы

* Секреты задаются только через переменные окружения (`.env` есть в `.gitignore` и `.dockerignore`).
* Доступ к боту ограничен по Telegram User ID (middleware, срабатывает до любых обработчиков и обращений к БД).
* Логи проходят через фильтр, который маскирует токен бота (в том числе внутри URL `api.telegram.org/bot…`), Bearer-токены и пароли в строках подключения к БД.
* Все запросы к БД строятся через ORM и параметризованы, поиск экранирует `%` и `_`.
* Контейнер приложения работает от непривилегированного пользователя, порт `/health` открыт только на `127.0.0.1`.
* **Бэкапы:** сервис `backup` делает `pg_dump` в `./backups` раз в `BACKUP_INTERVAL_HOURS` и хранит копии `BACKUP_KEEP_DAYS` дней. Вручную: `./scripts/backup.sh`. Восстановление: `./scripts/restore.sh backups/<файл>.dump`.

## 8. Автопокупка токенов Pons (Robinhood Chain)

Когда отслеживаемый аккаунт публикует **собственный пост** (не ответ, не репост, не цитату) с адресом контракта, например `$CA:0x8c21…b431`, бот:

1. находит в тексте все адреса `0x…` (до 3 на пост, ссылки `ponsfamily.com/launchpad/0x…` тоже распознаются);
2. проверяет через фабрику Pons v2 (`getLaunchedToken`), что это токен Pons в Robinhood Chain (chain ID 4663). Прочие адреса тихо пропускаются;
3. применяет ваши лимиты: сумма, макс. капитализация, налог создателя, дневной лимит в ETH и по числу покупок, баланс плюс резерв на газ;
4. покупает там же, где торгует ponsfamily.com:
   - токен ещё на **bonding curve** (phase 0): `curve.buy(quoteIn, minTokensOut, recipient)`;
   - токен уже в **пуле Uniswap v4** (phase 2): через Universal Router (`V4_SWAP`) в пул `ETH/токен` с хуком Pons;
5. присылает сообщение о покупке с кнопками **Продать 25% / 50% / 100%**. Продажа выполняется после подтверждения.

Каждый токен покупается **один раз**, даже если адрес опубликуют снова. Посты старше `TRADE_MAX_AGE_SECONDS` (например, после простоя сервера) не покупаются.

### Включение

1. Создайте **новый отдельный кошелёк** (например, в MetaMask: «Добавить аккаунт»), экспортируйте его приватный ключ и положите на него немного ETH в сети Robinhood Chain.
2. В `.env` укажите:
   ```
   TRADING_ENABLED=true
   WALLET_PRIVATE_KEY=0x…
   ```
3. Выполните `docker compose up -d`. В Telegram откройте **💰 Автопокупка токенов**, задайте сумму и лимиты и нажмите **🟢 Включить автопокупку**.

### Меню «💰 Автопокупка»

| Настройка | По умолчанию |
|---|---|
| Сумма покупки | 0.01 ETH |
| Макс. капитализация (по цене вашей покупки) | без лимита |
| Проскальзывание | 10% |
| Макс. налог создателя токена | 5% |
| Дневной лимит | 0.1 ETH и 10 покупок |
| Аккаунты для автопокупки | все отслеживаемые, переключаются по одному |

Там же есть **💼 Позиции** (баланс и примерная стоимость в ETH, кнопки продажи) и **📜 Сделки** (статусы, причины пропуска, ссылки на транзакции в обозревателе).

### Риски и ограничения

- **Скорость.** Пост приходит с задержкой опроса X API (5–60 с, в зависимости от настройки), поэтому первым покупателем бот не будет. Обязательно задайте лимит капитализации.
- **Ключ на сервере.** Тот, кто получит доступ к серверу, получит доступ к кошельку. Держите на нём только сумму, которую готовы потерять.
- **Мошенничество.** Аккаунт могут взломать, токен может оказаться скамом. Бот защищается лимитами, но не проверяет «качество» токена.
- Поддерживаются только токены Pons v2 в паре с ETH. Токены в паре с USDG или акциями пропускаются с объяснением.
- Транзакции идут по одной (один кошелёк, последовательные nonce). Если RPC упал после подписания, сделка проверяется по квитанции и **никогда не отправляется повторно**.

### Проверка на копии сети

```bash
anvil --fork-url https://rpc.mainnet.chain.robinhood.com --port 8546 --chain-id 4663
python -m tests.fork.check_fork 0x<токен на curve> 0x<токен в пуле>
FORK_RPC=http://127.0.0.1:8546 FORK_CURVE_TOKEN=0x… FORK_POOL_TOKEN=0x… pytest tests/test_fork_integration.py
```

Для проверки используйте **свежий** ключ. На известных тестовых адресах anvil в реальной сети стоит код-перехватчик (EIP-7702), который забирает пришедший ETH.

## 9. Расширение

* **Много аккаунтов:** аккаунт X общий для всех подписчиков, проверка планируется по `next_check_at`, параллельность задаётся через `MONITOR_CONCURRENCY`, захват строк атомарный (можно запустить несколько реплик мониторинга; исполнитель сделок должен работать в одном экземпляре — один кошелёк).
* **Новые источники** (ключевые слова, упоминания, filtered stream): добавьте сервис, который создаёт строки `events` и `notifications`. Доставка, дедупликация, история и статистика заработают без изменений.
* **Несколько чатов:** у каждого уведомления есть свой `chat_id`.
* **Экспорт CSV / Web Dashboard:** `EventRepository.history()` уже возвращает отфильтрованную историю, FastAPI-приложение (`api/app.py`) готово для новых эндпоинтов.
* **Пользователи и тарифы:** данные изолированы по `user_id`, а для лимитов тарифов достаточно проверки в `AccountManager.add()`.

## 11. Частые проблемы

| Симптом | Причина / решение |
|---|---|
| Бот отвечает «Доступ запрещён» | добавьте ваш ID в `TELEGRAM_ALLOWED_USER_IDS` и перезапустите |
| «🛑 Мониторинг X остановлен… 402» | закончились кредиты X API, пополните баланс в console.x.com |
| «… 401» | неверный `X_BEARER_TOKEN` |
| Аккаунт «🔴 Недоступен» | профиль удалён, заблокирован или стал закрытым |
| В `/health` поле `x_param_dialect: v2` | X перешёл на новые имена полей, клиент переключился автоматически |
